# PROTOCOL — Multi-Agent Task Protocol (Frontend Migration)

Rules for claiming, implementing, and **independently verifying** work so that later
agents can distribute tasks and validate each other's output.

## 1. Artifacts

| File | Role |
|---|---|
| `tasks.json` | **Canonical** task definitions + status |
| `BOARD.md` | Human-readable board, regenerated by `scripts/agents_board.py` |
| `decisions.md` | Append-only rationale log |
| `PLAN.md` | Vision, design system, architecture, milestones |
| `templates/` | Per-agent workspace templates |
| `.agents/<task-id>-<agent>/` | Per-task agent workspace |

## 2. Task lifecycle

```
todo → claimed:<agent> → in-review → verified
                    ↘ blocked ↗        ↘ rejected → (re-claim)
```

- **owner**: agent/user currently holding the task (`null` when unclaimed).
- **verifier**: the agent who must independently verify; **never** the implementer.
- **status**: one of the states above.
- **evidence**: path/description of proof (commands, screenshots, test output).
- **dep_override**: reason string recorded when a claim bypasses the dependency gate.
- **rejection**: reason string, required when status is `rejected`.

## 3. Claiming

1. Run `python scripts/agents_board.py --check` — must pass.
2. Pick a `todo` task whose `depends` are all `verified`.
3. Claim it with the CLI. This **enforces the dependency gate** and refuses if any
   dependency is not `verified`:

   ```bash
   python scripts/agents_board.py --claim FE-002 <your-agent-name>
   ```

   If (and only if) you are explicitly instructed to proceed despite unverified
   dependencies, override with a logged reason:

   ```bash
   python scripts/agents_board.py --claim FE-002 <your-agent-name> --force "reason"
   ```

4. Create `.agents/<task-id>-<agent>/` from `templates/` (copy BRIEFING, DISPATCH,
   progress, EVIDENCE, TESTPLAN and fill them in).

**Agent naming:** use a distinct, stable name per agent (e.g. `implementer-1`,
`verifier-1`). Never reuse the same name for an implementer and a verifier.

## 4. Implementing

- One task = one focused, PR-sized change.
- Read `decisions.md` first; do not contradict accepted decisions without a new entry.
- Meet **every** acceptance criterion listed on the task.
- **Run every test case** in the task's `tests` array (canonical in `tasks.json`);
  copy them into your workspace `TESTPLAN.md` and record PASS/FAIL + notes.
- **Strict parity** (D-007): preserve WS contracts, URL/token routing, anti-cheat,
  clipboard and replay behavior exactly.
- Record commands, outputs, screenshots and diffs in `.agents/<task-id>-<agent>/EVIDENCE.md`.
- Set `status: "in-review"` via the CLI (this **requires evidence** to be set first)
  and request a verifier.

### 4.1 Safety / scope rules

- **Never run destructive git commands** (`git checkout -- .`, `git restore .`,
  `git clean`, `git reset`, `git stash`) — they can delete unrelated tracked work.
  "Clean checkout" verification means reasoning about the branch state and using a
  scratch clone, not mutating the shared working tree.
- **Only create/modify files within your task's scope.** Do not delete or edit
  unrelated files. If you find unrelated files missing or modified, stop and report.
- Do not commit, amend, push, or open PRs unless explicitly instructed.

## 5. Verifying (independent — MANDATORY)

The verifier MUST be a different agent than the owner. The verifier:

1. Re-runs the task's acceptance commands **and every test case** on a clean checkout
   of the branch (do not trust the implementer's results — record your own).
2. Confirms each acceptance criterion with evidence (not by reading the diff alone).
3. Checks for regressions in adjacent behavior (WS, clipboard, timer, a11y, contrast).
4. Records findings in the task workspace `EVIDENCE.md` and `TESTPLAN.md`.
5. Sets `status: "verified"` **only** with evidence, otherwise `rejected` + reasons
   (`--reject <id> "reason"`).

Self-certification is forbidden. A task with `status: "verified"` and no `evidence`
fails `--check`, as does a task with no test cases or a `rejected` task with no reason.

## 6. Environment & command equivalents

The canonical deployment target is the **platform host** (D-006) with **Node/npm**.
Some authoring/verification environments differ; use these equivalents:

| Canonical | Accepted local equivalent | Notes |
|---|---|---|
| `npm run <script>` | `bun run <script>` | Bun 1.4.x runs the same Vite/Vitest scripts |
| `npm ci` | `bun install` | `bun.lock` is git-ignored; host generates `package-lock.json` |
| `rg <pattern>` | `grep -R` / PowerShell `Select-String` / the repo's Vitest audit test | `rg` may be absent |
| axe / browser checks | token-level contrast assertions + jsdom tests | see below |

**Browser (Playwright) tests are host-only.** They require `npx playwright install`
and network access. Locally, satisfy the same intent with Vitest + jsdom and mark
the browser leg **DEFERRED** in `TESTPLAN.md`; the platform-host verifier runs the
literal Playwright suite. A "PASS-by-equivalent + browser DEFERRED" is acceptable
for `in-review` but must be resolved at the milestone gate. On a Bun-only host,
Playwright's `webServer.command` (`npm run dev`) cannot start; pre-start
`bun run dev` first so `reuseExistingServer` picks it up (do not edit the config).

## 7. Done criteria (per task)

- [ ] All acceptance criteria met and demonstrated.
- [ ] Independent verifier signed off with evidence.
- [ ] No new lint/type/test failures.
- [ ] Docs/decisions updated when behavior or interfaces changed.

## 8. Board commands

```bash
python scripts/agents_board.py                         # regenerate BOARD.md + summary
python scripts/agents_board.py --check                  # validate only; non-zero on violations
python scripts/agents_board.py --claim FE-002 <agent>   # enforce deps, then claim
python scripts/agents_board.py --claim FE-002 <agent> --force "reason"
python scripts/agents_board.py --status FE-002 in-review  # requires evidence
python scripts/agents_board.py --set-evidence FE-002 .agents/FE-002-<agent>/EVIDENCE.md
python scripts/agents_board.py --verify FE-002          # requires evidence
python scripts/agents_board.py --unclaim FE-002
python scripts/agents_board.py --reject FE-002 "reason"
```

Validation fails on: duplicate IDs, missing dependencies, dependency cycles, a task
missing acceptance criteria or test cases, an `impl` task missing a verifier,
`verified` without evidence, or `rejected` without a reason.

## 9. Parallel batches & verification profile

To move faster, up to **3 implementer agents** may run **concurrently**:

- **Disjoint file ownership is mandatory.** Each agent is given an explicit file list
  and a do-not-touch list; no two agents edit the same file.
- The **orchestrator pre-claims** the tasks and owns `tasks.json`. During a batch,
  agents must **not** run `scripts/agents_board.py`.
- During a batch, agents run only `bun run test`, `bunx tsc --noEmit`, `bun run lint`.
  The orchestrator runs `bun run build` and Playwright **once** after the batch (those
  write shared `web/dist` / bind port 5173).
- Agents flag any needed shared-file change (App.vue, main.ts, router, package.json,
  configs, `tests/setup.ts`, styles) instead of editing it; the orchestrator handles
  integration.

**Verification profile:** for small/low-risk tasks the orchestrator may verify by a
single consolidated suite run (lint + typecheck + unit + build + Playwright) plus diff
review, then mark `verified`. **Independent verifier agents are still required** at
milestone gates (`FE-V*`) and for high-risk boundaries (WS/terminal/VNC proxy, auth,
clipboard, anti-cheat, session lifecycle).
